# 게이트웨이·비전 코드 작성 준수 계획

2026-09-30 · 대상: PC팀 게이트웨이(라인 PRD P0-10), 비전(P0-11) 담당

> 이 문서는 게이트웨이와 ST3 비전 코드를 쓸 때 지킬 규칙과 순서다. 요구사항 자체는 `docs/prd.md`(라인 PRD)가 기준이고,
> 모니터링 웹과 주고받는 형식은 `monitoring-twin/server/schema.py`와 `monitoring-twin/docs/monitoring-twin-prd.md` 부록 B가 계약이다.
> 셋이 서로 다르면 PRD → 계약 → 이 문서 순으로 따르고, 이 문서를 고친다.
> "미정"·"가정" 항목은 추측으로 확정하지 않는다. 설정값이나 `TODO(미정): ...` 주석으로 남긴다.

## 1. 전체 구조와 책임

```
[PLC Q03UDV] <──MC 프로토콜(pymcprotocol)──> [게이트웨이 (Python)] ──WebSocket /ingest──> [모니터링 웹 서버] ──> 브라우저
[로봇1·2·3 Indy7] <──IndyDCP3──────────────> [게이트웨이]            (이벤트 + 관절각)
[비전 (ST3 카메라 1대)] ──판정 결과(경로 미정)──> [PLC 또는 게이트웨이]
```

| 모듈 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 게이트웨이 | PLC 비트 읽기·쓰기, PLC REQ에 따라 로봇 작업 지시, 로봇 상태·관절각 읽기, 웹으로 이벤트·관절각 전달 | 인터록·판정 결정 (PLC가 함), 웹에서 온 명령 실행 |
| 비전 | ST3에서 촬영·규칙 기반 판정, 결과와 NG 사유 전달, 판정 이미지 저장 | 로봇·컨베이어 제어, 최종 합격 확정 (PLC가 확정) |
| 모니터링 웹 | 게이트웨이 이벤트를 받아 표시·기록 (읽기 전용) | PLC·로봇·비전에 직접 연결, 명령 전송 (원격 조작은 W1-5) |

- 현장 장비는 게이트웨이와만 통신한다. 웹과 비전은 로봇·PLC에 따로 붙지 않는다 (비전→PLC 직접 경로는 아래 미정 항목).
- 비상정지는 하드웨어다 (P0-5). 게이트웨이·비전 코드 어디에도 비상정지를 대신하는 경로를 만들지 않는다.

## 2. 공통 규칙 (게이트웨이·비전 모두)

### 폴더 (제안, 첫 작업에서 확정)
```
gateway/        main.py, config.py, plc.py, robots.py, events.py, tests/, mock/
vision/         main.py, config.py, inspect.py, rules/, calib/, samples/(시험 이미지), tests/
monitoring-twin/  (기존 웹. 게이트웨이·비전은 이 폴더 코드를 고치지 않고 schema.py만 가져다 쓴다)
```

### 코드
- Python 3.12, 폴더마다 `.venv` 와 `requirements.txt`(버전 고정). 테스트는 pytest
- 이름: 파일·함수·JSON 키는 snake_case, 상태 값·작업 코드·NG 사유 코드는 대문자 (`BUSY`, `ROBOT3_SORT`, `TURRET_MISSING`)
- 표기: 위치 ST1~ST3, 로봇 `robot1`~`robot3`(이벤트에서는 숫자 1~3), 컨베이어 CV1(ST1)·CV2(버퍼)·CV3(ST2)·CV4(ST3)·CV5(회수)
- 설정은 `config.py` 한 곳 + 환경변수로 덮어쓰기. IP·주기·타임아웃·카메라 노출을 코드 안에 흩어 두지 않는다
- 비밀값(API 키 등)은 환경변수로만. 저장소에 올리지 않는다
- 시각: 모든 기록·이벤트의 시각은 시간대가 붙은 ISO 8601 (`2026-09-30T14:03:21.120+09:00`). PC 시계는 NTP로 맞춘다 (반영 지연 K3 계산이 이 시각에 달려 있음)

### 로그
- 표준 `logging`, 파일은 날짜별 (`logs/gateway_YYYY-MM-DD.log`). 한 줄에 시각·모듈·로봇/구간 번호·내용
- 반드시 남길 것: 연결·끊김·재접속, PLC REQ 수신과 로봇 지시·응답(BUSY/DONE/ERR), 비전 판정(가동 순번·결과·사유·소요 시간), 규격 검증 실패
- 예외는 잡아서 로그를 남기고 계속 돈다. 한 로봇·한 프레임의 오류로 전체 프로세스가 죽지 않게 한다

### 장비 없이 돌아가게
- 모든 기능은 모의 모드로 실행·테스트할 수 있어야 한다 (`GW_MODE=mock`, `VISION_MODE=mock`)
- 모의 PLC(비트 맵 딕셔너리), 모의 로봇(지시하면 정해진 시간 뒤 DONE, 설정으로 ERR), 모의 카메라(`samples/` 이미지 재생)를 둔다
- 실제 장비 코드와 모의 코드는 같은 인터페이스(같은 함수 이름·반환값)를 쓴다

## 3. 게이트웨이 규칙 (P0-10)

### 구조 (라인 PRD P0-10 그대로)
- PLC 통신과 웹 전송은 asyncio. 로봇은 로봇당 스레드 1개와 큐 (IndyDCP3 SDK가 동기 함수)
- PLC 쓰기는 한 태스크만 한다 (여러 곳에서 동시에 쓰지 않음)
- PLC에 하트비트 비트를 주기적으로 토글해 PLC가 게이트웨이 정지를 감지하게 한다 (주기 미정, 설정값)

### 로봇
| 로봇 | 위치 | IP |
|---|---|---|
| 로봇1 | ST1 | 192.168.3.2 |
| 로봇2 | ST2 | 192.168.3.3 |
| 로봇3 | ST3 | 192.168.3.4 |

### 로봇 동작 방식 (2026-09-30 결정)
- 로봇 동작은 **Conty 앱 프로그램을 쓰지 않고, 게이트웨이의 Python IndyDCP3(`neuromeka` 패키지)로 직접 지시**한다. 제어기에 저장된 프로그램에 의존하지 않으므로 동작의 기준은 이 저장소의 코드와 경유점 파일이다
- 작업 코드별 동작 = 경유점 목록. `gateway/motions/{작업 코드}.json`에 순서대로 둔다 (관절각 또는 TCP 좌표, 이동 방식, 속도, 툴 I/O). 좌표 숫자를 코드에 박지 않는다
- 경유점 얻기: 로봇을 직접 교시(손으로 옮기기 또는 티치 펜던트 조그)로 위치에 둔 뒤, 교시 도구(`gateway/teach.py`)가 `get_control_data()`의 `q`·`p`를 읽어 경유점 파일에 추가한다. 파일은 git으로 관리하고, 바꿀 때 날짜·이유를 커밋 메시지에 남긴다
- 모션 명령(관절 이동·직선 이동 등)은 호출 즉시 돌아오므로, 완료는 상태를 폴링해 판단한다. 정확한 함수 이름·인자·완료 판정 방법은 설치한 `neuromeka` 버전의 IndyDCP3 문서로 확인해 `gateway/robots.py` 머리 주석에 적는다 (TODO(미정): 버전 고정 후 확인)
- 속도·가속 상한은 설정값. 처음 시험은 저속(상한의 30% 이하)으로 한다. 로봇 없는 동작 시험은 게이트웨이의 모의 로봇(`GW_MODE=mock`)으로 한다
- **실제 로봇에 시뮬레이션 모드 명령을 보내지 않는다.** 게이트웨이·교시 도구·시험 스크립트 어디에서도 `set_simulation_mode` 등 제어기 운전 모드를 바꾸는 호출을 쓰지 않는다
  (모드가 바뀐 줄 모르고 실제 이동을 지시하거나, 반대로 동작한 줄 알고 라인을 진행하는 사고를 막기 위해). 제어기 모드는 사람이 티치 펜던트에서만 바꾼다
    - 로봇 SDK 호출은 `gateway/robots.py`의 허용 목록을 거치게 하고, 운전 모드 변경 함수는 목록에 넣지 않는다. 목록에 없는 호출은 예외
    - 테스트: 게이트웨이 코드에 `set_simulation_mode` 문자열이 없는지 검사하는 pytest를 둔다

### 로봇 지시 규칙
- 작업 지시는 **PLC REQ를 받았을 때만** 보낸다. 작업 코드는 `ROBOT1_HULL_PLACE`, `ROBOT1_POWERPACK_MOUNT`, `ROBOT2_TURRET_MATE`, `ROBOT2_WELD_MOTION`, `ROBOT3_SORT` (P0-3)
- 모션 명령을 부르는 곳은 로봇별 작업 실행기 한 곳뿐이다. 웹·음성·시험 스크립트 등 PLC REQ 밖에서 로봇을 움직이는 경로를 만들지 않는다 (예외: 교시 도구는 모션 명령 없이 읽기만, 로봇 이동은 사람이 함)
- 실패 판정 → ERR: 작업 시간 초과(작업 코드별 설정값), 제어기 상태가 충돌·안전 위반·비상정지 등 이상 상태, SDK 예외. ERR이면 진행 중 모션을 멈추고 PLC에 ERR을 올린다. 자동 재시도하지 않는다 (복구는 사람이 확인 후)
- 게이트웨이가 종료되거나 로봇 스레드가 예외로 끝나면 진행 중 모션을 멈추는 명령을 먼저 보낸다. PLC는 하트비트 끊김으로 라인을 멈춘다
- 응답은 BUSY / DONE / ERR로 PLC와 웹에 같이 알린다. ERR는 사유를 로그와 `alarm` 이벤트로 남긴다
- 끊기면 2초 간격으로 다시 접속하고, 끊김·복구를 `link` 이벤트로 보낸다. 끊겼다 붙어도 하던 작업을 이어서 하지 않는다 (ERR 처리)

### 관절각 읽기 (웹 W1-1 대비)
- 작업 실행기가 완료 판정을 위해 어차피 상태를 폴링하므로, 그 루프에서 `get_control_data()`의 `q`(deg 6개)를 20 Hz로 함께 읽어 웹으로 보낸다. 로봇 연결을 따로 늘리지 않는다
- 웹 전송이 늦어도 폴링·지시를 기다리게 하지 않는다 (웹 큐에 넣고 끝). 3대 동시 20 Hz가 안 되면 주기를 낮추고 실제 값을 기록한다

## 4. 비전 규칙 (P0-11)

### 판정
- ST3 고정 카메라 1대, 고정 노출·고정 조명. 자동 노출·자동 화이트밸런스는 끈다
- 규칙 기반만 쓴다 (AI 모델은 P0 제외, P1-9). 검사 항목: 파워팩 장착 상태, 포탑 정렬·이음 간격·기울기, 부품 누락·방향
- 판정 기준값(허용 픽셀·각도 등)은 `rules/`의 설정 파일에 둔다. 코드에 숫자를 박지 않는다. 기준을 바꾸면 파일에 날짜와 이유를 남긴다
- 캘리브레이션 결과는 `calib/`에 날짜별로 보관하고, 판정 결과에 어떤 캘리브레이션을 썼는지 적는다
- 판정 시간 상한을 둔다 (가정 2초, 설정값). 넘으면 NG가 아니라 `VISION_TIMEOUT` 알람을 내고 PLC 규칙에 따른다

### 출력
- 판정 1건 = `{run_no, ts, ng, reason, measures, image}`
    - `ng`: 비전 판정만 (최종 합격 확정은 PLC)
    - `reason`: NG 사유 코드 하나 (대문자). 여러 개면 가장 중요한 것 하나 + `measures`에 전부
    - `measures`: 항목별 측정값 (예: `{"turret_angle_deg": 1.2, "gap_mm": 0.8}`)
    - `image`: 저장한 이미지 파일 이름
- NG 사유 코드는 비전·PLC팀이 목록으로 합의한다. 합의 전 예시: `TURRET_MISSING`, `POSITION_OFFSET`, `POWERPACK_MISSING`, `TURRET_TILT`. 로봇 실패 코드(`ROBOT1_ERR` 등)와 겹치지 않게 한다
- 이미지는 `images/YYYY-MM-DD/run_{run_no:05d}_{OK|NG}.jpg`로 저장한다 (웹 W1-3 비전 결과 이미지와 K2 재검토용). 보관 기간은 설정값

### 검증 (K2)
- `samples/`에 정상·불량 이미지를 항목별로 모아 두고, pytest로 기대 판정과 비교한다
- K2 측정: 누락·방향·위치 불량 검출 90% 이상, 정상품 오검출 5% 이하 (각 30장 이상). 결과는 표로 남긴다

## 5. 모니터링 웹 연동

### 계약
- 이벤트 형식은 `monitoring-twin/server/schema.py`가 단 하나의 기준이다 (`line`, `conveyor`, `robot`, `result`, `alarm`, `link`)
- 게이트웨이 테스트는 자기가 만든 이벤트를 `schema.parse_event()`로 검증한다. 게이트웨이가 형식을 따로 정의하지 않는다
- 형식을 바꿔야 하면 게이트웨이에서 먼저 바꾸지 말고 `schema.py`와 부록 B를 함께 고친 뒤 양쪽 테스트를 돌린다

### 보내는 방법 (웹 측 입구는 아직 없음, M4에서 추가)
- WebSocket `/ingest`에 상시 연결해 JSON 한 건씩 보낸다. 끊기면 지수 백오프로 재접속 (최대 5초)
- 재접속 직후에는 현재 상태(line, conveyor 5개, robot 3대, link)를 한 번 다시 보낸다 (웹 스냅샷 동기화)
- `ts`는 게이트웨이 시각. 웹은 이것과 수신 시각의 차이로 반영 지연(K3)을 잰다
- 상태가 바뀔 때만 보낸다. 같은 값을 주기적으로 반복하지 않는다 (예외: 하트비트)
- 하트비트: 1초마다 `{"type":"link","ts":...}` (가정). 웹은 2초 동안 아무것도 안 오면 게이트웨이 끊김으로 표시
- `link`는 바뀐 필드만 보낸다 (부분 갱신)
- 웹이 응답하지 않아도 PLC·로봇 처리는 멈추지 않는다. 웹 전송은 큐에 넣고 따로 보내며, 큐가 차면 오래된 것부터 버리고 로그를 남긴다

### 이벤트별 발생 시점
| 이벤트 | 보낼 때 |
|---|---|
| `line` | 시작·정지·일시정지·비상정지 비트가 바뀔 때 |
| `conveyor` | `CV#_STATE`가 바뀔 때 (EMPTY/ARRIVING/HOLD/DEPARTING) |
| `robot` | REQ 지시(BUSY), DONE, ERR, READY 복귀. `job`에 작업 코드 |
| `result` | PLC가 최종 판정을 확정했을 때 (`run_no`, `ng`, `reason`). 비전 판정이 아니라 PLC 확정값 |
| `alarm` | 발생(`cleared:false`)과 해제(`cleared:true`) 두 번 |
| `link` | PLC·로봇 연결이 바뀔 때 + 하트비트 |

### 관절각 (웹 W1-1, 계획: `monitoring-twin/docs/monitoring-twin-plan.md` W1-1)
- 같은 `/ingest`로 `{"type":"joints","robot":1,"ts":"...","q":[6]}` (가정, 확정 시 부록 B에 추가)
- 20 Hz, 로봇이 끊기면 보내지 않는다. 웹은 저장하지 않고 최신값만 중계한다

### 비전 결과가 웹에 가는 길
- 비전은 웹에 직접 보내지 않는다. 판정은 PLC 확정을 거쳐 게이트웨이의 `result`로 간다
- 이미지는 비전 PC의 `images/`에 남기고, 웹 W1-3을 할 때 파일 이름 규칙(`run_no`)으로 찾는다 (전달 방식은 그때 정함)

| 단독 | 모의 PLC·모의 로봇으로 REQ→BUSY→DONE, ERR 경로(시간 초과·이상 상태) pytest, 경유점 파일 형식 검사 | `samples/` 이미지로 항목별 판정 pytest |
| 계약 | 출력 이벤트 전부 `schema.parse_event()` 통과 | 출력 형식 필드 검사 |
| 웹 연동 | 모의 모드 게이트웨이 → 웹 `/ingest` → 트윈 화면에서 `monitoring-twin/mock/scenarios`와 같은 흐름 확인 | 모의 판정 결과가 `result`로 웹 기록 페이지에 남는지 확인 |
| 실장비 | 로봇 3대·PLC와 가동 1회가 웹 화면과 일치, K3 1초 이하 | K2 측정 (각 30장 이상) |

- 커밋 전: 해당 폴더 pytest 통과. `test.skip`이나 비어 있는 테스트로 통과시키지 않는다
- 매 단계 보고: 만든 것, 확인한 방법(테스트 이름), 남은 문제, 가정으로 처리한 부분

## 7. 순서

1. 1주차: PLC↔PC 비트 맵(I/O 할당표) 확정, NG 사유 코드 목록 초안, 이 문서의 폴더·설정 확정
2. 게이트웨이 모의 모드 + 계약 테스트 / 비전 시험 이미지 수집 + 규칙 판정
3. 웹 `/ingest` 추가(모니터링 M4) 후 모의 게이트웨이로 웹 연동 확인
4. 실장비: 경유점 교시(로봇별) → 저속 시험 → 로봇 1대 → 3대, PLC 연결, 비전 실측 (K2), 연속 30회 (K3, 기록 누락 0건)
5. 여유가 있으면 관절각 20 Hz (웹 W1-1)

## 8. 정해야 할 것

| 항목 | 누가 | 없을 때 가정 |
|---|---|---|
| PLC↔PC I/O 할당표 (비트 맵) | PLC팀 + PC팀 | 모의 PLC 딕셔너리 |
| 비전 판정이 가는 길 (PLC 경유 / 게이트웨이 직접) | 비전 + PLC팀 | PLC 경유 |
| NG 사유 코드 목록 | 비전 + PLC팀 | 위 예시 코드 |
| 게이트웨이와 웹 서버를 한 프로세스로 둘지 | 게이트웨이 + 웹 | 별도 프로세스, `/ingest`로 연결 |
| PLC 하트비트 주기, 비전 판정 시간 상한 | PLC팀, 비전 | 설정값 (비전 2초) |
| `robot` 이벤트의 부가 정보(슬롯, PASS/FAIL) | 게이트웨이 + 웹 | 보내지 않음 |
| 관절각 메시지 형식·주기 | 게이트웨이 + 웹 | 위 형식, 20 Hz |
| IndyDCP3 모션 함수·완료 판정 방법, `neuromeka` 버전 | 게이트웨이 | 문서 확인 전 모의 로봇으로만 개발 |
| 작업 코드별 시간 초과·속도 상한 | 게이트웨이 + PLC-B | 설정값 (저속) |
