# 모니터링 웹·디지털 트윈 구현 계획

원칙: 규격 먼저, 모의 데이터로 화면 먼저, 실제 장비 연결은 나중. 마일스톤마다 완료 조건을 확인하고 멈춰서 보고한다.
순서: M1 → M2 → B1 → M3 → M4 → M5 → B2 → M6 (B는 Blender 3D 모델 작업. M4는 현장 일정에 따라 B2와 순서를 바꿀 수 있음)
주차는 6주 프로젝트 기준이며, 다른 팀 일정에 따라 사람이 조정한다.

## 다른 팀에서 받아야 할 것

| 받을 것 | 주는 팀 | 필요한 마일스톤 | 없을 때 |
| --- | --- | --- | --- |
| 이벤트 규격 v0 합의 | PC팀 게이트웨이 | M1 | 부록 B 초안으로 진행 |
| 변수 규칙 | PC팀 | M1 | snake_case·대문자 상태값 가정 |
| PLC↔PC I/O 할당표 | PLC팀 + PC팀 | M4 | 모의 데이터만 사용 |
| 전차 3D 모델 | 디자인팀 | B2 | 박스 placeholder 유지 |
| 전차·팔레트 크기 (실물 치수) | 디자인팀 | B1, B2 | 라인 PRD 가정값 (전차 165×110×60~70 mm, 파워팩 120×80 mm, 팔레트 폭 약 120 mm) |
| 컨베이어·스테이션 GLB, Indy7 URDF | 디자인팀 3D 모델 담당 | M3 | **받음** (`../web/assets/`) |
| GLB 치수 기준 (현재 모델은 PRD 가정의 약 2배) | 디자인팀 | B1 | 현재 `P` 값 유지 |
| 트레이 위치·구획 | PLC팀 (라인 PRD P0-12 미정) | B1 | 파라미터 가정값 |

트레이·보관창고·구간 표시와 전차 단계별 모델은 받지 않고 이 작업에서 직접 만든다 (B1, B2).
| NG 사유 코드 목록 | 비전·PLC팀 | M5 | 문자열 그대로 표시 |

    - 2026-09-30 설치: winget은 사용자 범위 설치 파일이 없어 실패 → 포터블 zip Blender 4.5.14 LTS (sha256 확인)를 `C:\Users\user\tools\blender-4.5.14-windows-x64\blender.exe`에 둠
    - 2026-09-30 완료: 노드 45 → 67개 (기존 이름 모두 유지), 삼각형 51,712 → 77,300, GLB 1.43 → 1.95 MB. 트레이는 ST3 ±0.38 m, 보관창고는 헤드 드럼 너머 x = 2.18 m
- 추가할 오브젝트 (크기·위치는 `P` 딕셔너리 파라미터로)
    - `Tray_Pass`, `Tray_Fail`: ST3 옆, 로봇3 작업 범위 안. 수량 표시용 전차 자리(`Tray_Pass_Slot_01~`)
    - 보관창고: CV5(회수 구간) 끝, 헤드 드럼 너머에 둔다. 서보모터가 **3단 선반 전체(매거진)를 상하로 움직여** 채울 칸을 벨트 높이에 맞추고, 팔레트는 벨트에서 그 칸으로 바로 들어간다 (확정, 2026-09-30)
        - `Storage`: 고정부 (기둥·가이드 레일·서보 모터 박스)
        - `Storage_Rack`: 움직이는 3단 선반. 기준점 = 1칸 선반 윗면 중심. three.js는 이 오브젝트의 높이만 움직인다
        - `Storage_Slot_01`~`03`: `Storage_Rack`의 자식, 각 칸 팔레트 자리 빈 오브젝트 (아래 칸부터 01). custom property `level`. 들어간 팔레트는 이 자리에 붙여 선반과 함께 움직인다
        - 파라미터: `storage_slots = 3` (확정), `storage_pitch` 칸 간격 (가정 0.18 m, 전차를 얹은 팔레트 높이 + 여유)
        - 선반 높이: k칸을 벨트에 맞출 때 1칸 윗면 = 벨트 윗면 - (k-1) × 칸 간격. 스트로크 = (칸 수 - 1) × 칸 간격을 `EV_Line.userData`에 기록 (three.js 애니메이션 범위)
    - `Zone_CV1`~`Zone_CV5`: 구간 경계 빈 오브젝트. custom property `cv`, `x_start`, `x_end` → three.js가 구간 좌표를 여기서 읽음 (하드코딩 없앰)
    - `Sensor_CV2_LED`, `Sensor_CV5_LED`: 버퍼·회수 구간 도착 센서 (기존 `Sensor_ST#_LED`와 같은 재질 방식)
- 결정 전까지 그대로 두는 것: 전체 치수(`P`), `Camera_ST2` (라인 PRD P0은 ST3 카메라만. `P["cameras"]` 파라미터로 끌 수 있게만 함)
- 오브젝트 이름은 필요하면 바꿀 수 있다 (사람 승인). 바꾸거나 추가하면 같은 작업에서 루트 `CLAUDE.md` 이름 규칙 표, `conveyor_gen.py` 머리 주석, `web/preview_src.html`의 `getObjectByName` 호출을 함께 고친다
- 완료 조건
    - 백그라운드 재생성 성공, 재생성 전후 이름 목록 비교 결과를 보고 (바뀐 이름은 위 세 곳에 모두 반영됨)
    - `python web\build.py` 미리보기가 그대로 동작
    - GLB 크기·삼각형 수를 보고에 기록 (기존: 로봇 포함 약 617k 삼각형)

### B2. 전차 단계별 모델 (3~5주차, M6 앞)

전차 모델은 디자인팀이 보내 준다 (2026-09-30 결정). 받은 원본을 Blender에서 정리한다.

- 기준 치수: 라인 PRD 가정 (길이 약 165 × 너비 약 110 × 높이 60~70 mm, 궤도 포함). 파워팩 120×80 mm는 차체 후방 Bay 포켓(123×83)에 들어감. 포탑은 차체 상부 포탑 링 위
- 파이프라인
    1. 디자인팀 모델 파일을 받은 그대로 `blender/source/`에 둔다 (받은 날짜·파일은 그 폴더 `README.md` 표에 기록)

    3. 받은 모델이 부품 분리에 맞지 않으면 디자인팀에 분리를 요청. 급하면 대안: 스크립트 로우폴리 모델링 (박스·원기둥 조합)
- 오브젝트 이름: `Tank_Hull`(바퀴·궤도 포함), `Tank_Powerpack`, `Tank_Turret`. 기준점 = 각 부품의 결합 위치, 팔레트 둥지 위에 그대로 얹히게
- 삼각형 예산: 전차 1대 3만 이하 (가정). 팔레트 3~4개 + 트레이 위 전차가 동시에 보여도 30 fps 유지
- 완료 조건
    - three.js에서 세 부품을 따로 켜고 끌 수 있음, 팔레트 위에 단계별로 맞게 쌓임
    - `blender -b -P blender\tank_prepare.py`로 다시 만들 수 있음 (디자인팀 원본은 `blender/source/`에 보관)

### W1-1. 로봇 관절 동기화 계획 (2026-09-30, 구현은 M6 이후)

참고 구현: https://github.com/woogijeong/Digital_twin_indy7 (FastAPI가 IndyDCP3 `get_control_data()`를 20 Hz로 읽어
`/ws/telemetry`로 최신 프레임만 방송, 저장 안 함, 브라우저는 받은 `q`를 그대로 적용). 단, 이 웹은 로봇에 직접 연결하지 않으므로
읽기는 게이트웨이로 옮기고 전달 구조만 가져온다.

```
Indy7 ×3 ──IndyDCP3──▶ 게이트웨이 ──WebSocket /ingest (상시 연결)──▶ 웹 서버 ──/ws──▶ 브라우저
            20 Hz 읽기        (이벤트 + 관절각)                  관절각은 저장·스냅샷 없이 최신값만 중계
```

- 게이트웨이 (PC팀)
    - 로봇마다 `get_control_data()`의 `q`(deg 6개)를 20 Hz로 읽는다 (로봇1 192.168.3.2, 로봇2 .3, 로봇3 .4 — 라인 PRD). SDK가 동기라 스레드에서 호출 (참고 구현 `indy.py`의 `to_thread`)
    - 게이트웨이가 로봇 동작도 IndyDCP3로 지시하므로(Conty 앱 사용 안 함), 작업 완료 판정용 상태 폴링 루프에서 `q`를 같이 읽는다. 웹 전송이 지시·폴링을 늦추지 않게 한다 (`docs/gateway-vision-rules.md` 3장)
    - 관절각 메시지 (가정, 확정 시 PRD 부록 B에 추가): `{"type":"joints","robot":1,"ts":"...","q":[6]}`. 로봇이 끊기면 보내지 않는다
- 웹 서버 (이 웹)
    - 게이트웨이 입구: WebSocket `/ingest` 하나로 기존 이벤트와 관절각을 함께 받는다 (M4 입구와 공용. 초당 60건이라 요청마다 HTTP POST보다 상시 연결)
    - `joints`는 `ingest()`(스냅샷 갱신·SQLite 저장·전체 스냅샷 방송)를 거치지 않는다. 로봇별 최신값만 두고 브라우저로 바로 중계
    - 느린 브라우저는 밀린 관절각을 버리고 최신값만 받는다 (참고 구현의 크기 1 큐)
- 화면 (이 웹)
    - 받은 `q`를 `setJoints()`로 그대로 적용. 20 Hz라 보간 없이 시작하고, 끊겨 보이면 그때 보간 추가
    - 관절각이 1.5초 넘게 안 오면 지금의 작업 상태 기반 데모 자세로 돌아간다 (모의 시나리오도 이 경로로 계속 동작)
- 모의: `mock/`에 관절각 발생기를 추가해 로봇 없이 20 Hz 경로를 시험한다
- 완료 조건
    - 실제 자세와 화면 자세가 눈으로 일치, 관절각 수신 간격이 평균 50 ms 근처
    - 관절각을 켜도 이벤트 반영 지연(K3)과 SQLite 크기가 변하지 않음 (관절각은 저장하지 않음)
- 사람이 정할 것: 게이트웨이 담당과 관절각 메시지 형식·주기(20 Hz 제안) 확정, 게이트웨이 프로세스 위치 (`server/main.py`의 `TODO(미정)`)
