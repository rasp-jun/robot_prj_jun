# 모니터링 웹·디지털 트윈 PRD

> 라인 전체 PRD의 P0-14(웹 모니터링 트윈)와 P1-5(재작업 이력 화면)를 구현 단위로 나눈 문서.
> 기능 번호는 W0-n(핵심), W1-n(추가)으로 써서 라인 PRD의 P0-n과 구분한다.

## 1. Why - 목적

- 해결할 문제
    - 컨베이어 5구간, 로봇 3대, ST3 판정 상태를 한 화면에서 볼 수 없음
    - 로봇 ERR·NG가 생겨도 어느 팔레트, 어느 위치에서 생겼는지 추적이 어려움
    - 포트폴리오 열람자가 라인 동작과 KPI를 빠르게 이해할 화면이 필요함
- 목표
    - 현장 상태를 실시간으로 보여 주는 3D 트윈과 모니터링 대시보드(상태·알람·가동 기록·KPI)를 웹 하나로 제공
    - 현장 장비 없이도 모의 이벤트로 단독 개발·시연 가능
- 성공 기준
    - 반영 지연: 현장 변화 → 화면 표시 1초 이하 (라인 PRD K3, 95번째 백분위, 가정)
    - 상태 일치: 연속 가동 30회 동안 구간·로봇·판정 표시 불일치 0건 (가정: 30회)
    - 기록: 모든 가동의 판정·NG 사유·사이클 타임 조회 가능 (라인 PRD P0-13)
    - 연결 끊김: 게이트웨이·PLC·로봇 연결 끊김을 3초 안에 화면에 표시 (가정: 3초)
- 제약
    - P0은 읽기 전용: 웹에서 PLC·로봇에 쓰지 않음 (원격 조작은 W1-5)
    - 웹은 게이트웨이만 바라봄. PLC·로봇과 직접 통신하지 않음
    - 제품 ID 없음. 화면의 추적 단위는 가동 순번과 팔레트 위치
    - 기술: FastAPI + WebSocket, three.js + Blender GLB (라인 PRD P0-14)
- 범위 밖
    - 웹에서 로봇 좌표·속도 지령, 클라우드 배포, 로그인·권한 관리

## 2. Who - 타깃 사용자

- 라인 운영자 (시연·운전)
    - 니즈: 라인이 도는지, 어디서 멈췄는지, NG 원인이 무엇인지 한눈에 확인
- 팀 개발자 (PLC팀·게이트웨이·비전)
    - 니즈: 신호 값(구간 상태, 로봇 READY/BUSY/DONE/ERR)과 이벤트 로그로 디버깅
- 포트폴리오 열람자 (면접관, 평가자)
    - 니즈: 3D 트윈으로 공정 흐름 이해, KPI 결과 확인
- 재작업 담당자 (P1)
    - 니즈: 가동별 NG 사유와 재작업 횟수 조회
- 만드는 사람
    - PC팀 모니터링 웹 담당: 서버·화면·트윈 전체 (1주차 역할 배분 후 확정)
    - PC팀 게이트웨이 담당: 이벤트 발행 (W0-1)
    - 디자인팀 3D 모델 담당: 컨베이어·스테이션 GLB 원본(`../blender/conveyor_gen.py`), 실물 치수
    - 트윈 작업(이 문서 범위): 트레이·보관창고·구간 표시를 `conveyor_gen.py`에 추가, 전차 단계별 모델 제작 (계획 B1·B2)
    - 인터페이스: 게이트웨이↔웹은 부록 B 이벤트 규격, PLC팀↔PC팀은 I/O 할당표

## 3. User Flow

1. 게이트웨이와 웹 서버를 실행하고 브라우저로 접속
    - 게이트웨이 미연결 → 상단에 "연결 끊김" 배너, 3D는 마지막 상태를 회색으로 표시
    - 현장 장비 없이 개발할 때는 모의 이벤트 발생기(W0-0)에 연결
2. 화면이 GLB 모델을 불러오고 현재 상태 스냅샷을 받아 초기화 (W0-2)
3. 운영자가 현장에서 시작 버튼을 누름 → 화면의 라인 상태가 RUN으로 바뀜
4. 팔레트가 구간을 이동하면 3D 팔레트가 ST1 → 버퍼 → ST2 → ST3 → 회수 구간으로 따라 이동
5. PLC가 작업을 지시(REQ, PLC 요청 비트)하면 로봇 상태가 READY → BUSY → DONE으로 바뀌고, 바뀔 때마다 로봇 색과 현재 작업 코드가 바뀜 (REQ는 로봇 상태가 아님, 라인 PRD P0-3)
    - ERR → 알람 패널에 추가, 해당 팔레트를 NG(빨강)로 표시, 이후 위치는 "작업 생략"으로 표시
6. ST3에서 PLC가 판정을 확정하면 팔레트에 합격/불합격을 표시하고, 가동 기록 표에 한 줄 추가
7. 로봇3가 전차를 합격/불합격 트레이로 옮기면 트레이 수량이 늘고, 팔레트는 보관창고로 이동
8. 비상정지 → 전체 적색 배너, 복귀하면 해제 시각과 함께 알람 기록에 남음
    - 연결 끊김(게이트웨이·PLC·로봇) → 끊긴 대상만 회색 + 알람, 재연결하면 스냅샷으로 다시 동기화
9. 가동이 끝나면 KPI 화면에서 성공률·사이클 타임을 확인하고 CSV로 내보냄

## 4. 기능 요구사항

### P0 - 핵심 기능

- W0-0 모의 이벤트 발생기
    - 동작: 실제 게이트웨이와 같은 규격(부록 B)의 이벤트를 시나리오 파일대로 보냄 (정상 1대, 로봇1 ERR, 비상정지, 연결 끊김)
    - 입력: `mock/scenarios/*.json` (이벤트 목록 + 간격)
    - 출력: WebSocket 이벤트
    - 완료 조건: 현장 장비 없이 User Flow 1~9를 화면에서 재현
- W0-1 상태 수집과 이벤트 발행 (게이트웨이 측)
    - 동작: 게이트웨이가 PLC 디바이스를 주기적으로 읽고(가정: 100 ms) 바뀐 값만 이벤트로 발행
    - 입력: I/O 할당표의 `CV#_STATE`, 로봇 READY/BUSY/DONE/ERR와 작업 코드, 라인 상태, 판정(`ng`, NG 사유), 가동 순번, 하트비트
    - 출력: 부록 B의 JSON 이벤트
    - 완료 조건: 현장 변화 누락 0건, 반영 지연 1초 이하(K3)
    - 미정: 게이트웨이와 웹 서버를 같은 프로세스로 둘지 (가정: 같은 프로세스, 내부 큐로 전달)
- W0-2 웹 서버와 스냅샷
    - 동작: FastAPI가 WebSocket(`/ws`)으로 이벤트를 방송하고, `GET /api/snapshot`으로 현재 전체 상태를 제공
    - 입력: W0-1 이벤트
    - 출력: 스냅샷 JSON (라인, 구간 5개, 로봇 3대, 연결, 활성 알람, 마지막 가동)
    - 완료 조건: 새로고침·재접속 후 1초 안에 현장과 일치, 브라우저 2개 동시 접속 시 같은 화면
- W0-3 3D 트윈 뷰
    - 동작: three.js로 GLB를 불러와 컨베이어 5구간, ST1~ST3, 로봇 3대, ST3 카메라, 합격/불합격 트레이, 보관창고를 배치
    - 팔레트: 구간 상태(EMPTY/ARRIVING/HOLD/DEPARTING)에 따라 이동. 센서 사이 구간은 보간 애니메이션
    - 팔레트 위 전차: 진행 단계에 따라 하부 차체 → 파워팩 → 포탑 모델을 차례로 표시
    - 로봇: 상태 색 READY 회색, BUSY 주황, DONE 초록, ERR 빨강 (루트 `CLAUDE.md`의 GLB 상태 링 색 체계에 READY 회색을 더함). 관절 동기화는 W1-1
    - 장면 구조: `Line > Conveyor(CV1~CV5) · Stations(ST1~ST3) · Robots(Robot1~3) · Pallets · Trays(Pass, Fail) · Storage`
    - 3D 모델: `../web/assets/ev_line_conveyor.glb`(벨트 1개, 스테이션 x = -1.1 / 0 / 1.1 m)와 Indy7 URDF·STL을 그대로 쓴다. 5구간은 벨트 위 x 좌표로 나눈다 (가정: CV1 -1.1, CV2 -0.55, CV3 0, CV4 1.1, CV5 1.7. 계획 B1 이후에는 GLB의 `Zone_CV#`에서 읽음). 트레이·보관창고는 B1(보관창고 = CV5 끝, 서보가 3단 선반 전체를 상하로 움직여 채울 칸을 벨트 높이에 맞춤. 팔레트가 칸에 들어가면 선반이 다음 빈 칸 높이로 이동하는 애니메이션), 전차 단계별 모델(`Tank_Hull`·`Tank_Powerpack`·`Tank_Turret`)은 B2에서 만들고, 그 전까지는 박스 placeholder
    - 입력: 스냅샷 + 이벤트, `../web/assets/` (GLB 원본은 디자인팀 `blender/conveyor_gen.py`로 재생성, 복사하지 않음)
    - 완료 조건: 연속 가동 30회 동안 현장과 표시 불일치 0건, 노트북에서 30 fps 이상 (가정)
- W0-4 상태 패널
    - 동작: 라인 상태(STOP/RUN/PAUSE/ESTOP), 구간 5개 상태, 로봇 3대 상태와 현재 작업 코드, 게이트웨이·PLC·로봇 연결 상태 표시
    - 완료 조건: 화면 값과 PLC 모니터 값이 일치, 연결 끊김 3초 안에 표시
- W0-5 알람 패널
    - 동작: 로봇 ERR, 비상정지, 연결 끊김을 발생 시각·출처·내용으로 목록화, 해제되면 해제 시각 기록
    - 출력: 활성 알람(상단), 알람 이력(SQLite, 가정)
    - 완료 조건: 발생 1초 안에 표시, 서버 재시작 후에도 이력 유지
- W0-6 가동 기록 표
    - 동작: 가동마다 가동 순번, 시작·종료 시각, 판정, NG 사유, 위치별 작업 시간(ST1·ST2·ST3)을 저장하고 표로 표시, CSV 내보내기
    - 입력: 로봇 BUSY→DONE 시각, ST3 판정 이벤트
    - 완료 조건: 모든 가동이 빠짐없이 남음(라인 PRD P0-13), 사이클 타임으로 K5 병목 구간 확인
- W0-7 KPI 요약
    - 동작: 가동 기록에서 계산해 표시. K1 조립 성공률(로봇1, 로봇2), K3 반영 지연(95번째 백분위), K5 위치별 평균 사이클 타임, K6 용접 모션 완주율
    - 완료 조건: CSV로 손 계산한 값과 일치

### P1 - 추가 기능

- W1-1 로봇 관절 동기화
    - 동작: 게이트웨이가 IndyDCP3로 관절각을 읽어 전달(`get_control_data()`의 `q`, Digital_twin_indy7에서 사용 확인), 3D 로봇 6축을 실제 자세대로 회전. 기존 digital_twin2(three.js + FastAPI) 코드 재사용 검토
    - 입력: 로봇 3대 관절각 (가정: 로봇당 20 Hz, 게이트웨이 경유. 계획은 monitoring-twin-plan.md W1-1)
    - 완료 조건: 실제 자세와 화면 자세가 눈으로 일치, 로봇 작업 지연(K3)에 영향 없음
    - 전제: 축별로 움직이는 Indy7 모델 (URDF로 충족)
- W1-2 재작업 이력 화면 (라인 PRD P1-5)
    - 동작: 가동별 NG 사유와 재작업 회차 조회
    - 미정: 제품 ID가 없어서 재투입한 전차를 이전 가동과 연결하는 방법
- W1-3 비전 결과 이미지
    - 동작: ST3 판정 이미지와 NG 영역을 가동 기록에서 열람. 버퍼 카메라(라인 PRD P1-13) 도입 시 함께 표시
    - 입력: 비전 PC가 저장한 이미지 경로
- W1-4 기능 검사 결과 (라인 PRD P1-2·P1-3)
    - 동작: ST1 자체 테스트 결과(mV, mA, flags)와 BLE 수신 상태 표시
- W1-5 원격 조작 요청
    - 동작: 시작·일시정지·재개·리셋 버튼이 PLC 요청 비트만 올림. 실행 여부는 PLC 인터록이 결정, 시작·리셋은 확인 창. 비상정지는 하드웨어만
    - 완료 조건: 인터록 조건이 안 맞으면 거부되고 화면에 사유 표시, 모든 요청이 감사 로그에 남음
- W1-6 리플레이
    - 동작: 저장한 이벤트로 과거 가동을 3D에서 다시 재생 (W0-0과 같은 재생기 사용)
- W1-7 KPI 추가
    - 동작: 위치 반복정밀도, MTTR, FPY 표시
    - 미정: 라인 PRD에 KPI로 추가할지 결정 후 착수

## 부록 A. 시스템 구조

```
[PLC Q03UDV] <--MC 프로토콜--> [게이트웨이 (Python)] --이벤트--> [웹 서버 FastAPI /ws /api, SQLite] --WebSocket--> [브라우저: 3D 트윈 + 대시보드]
[로봇1·2·3 Indy7] <--IndyDCP3--> [게이트웨이]
[비전 PC (ST3)] --경로 미정--> [게이트웨이]
```

- 현장 장비는 게이트웨이와만 통신하고, 웹은 게이트웨이가 내보낸 이벤트만 받음
- 비전 결과가 PLC를 거칠지 게이트웨이로 직접 올지는 미정

## 부록 B. 이벤트 규격 (v0 초안)

- 공통 필드: `type`, `ts`(ISO 8601, 게이트웨이 시각). 값은 PLC↔PC I/O 할당표가 확정되면 맞춤

| type | 필드 | 예 |
| --- | --- | --- |
| line | state | `{"type":"line","state":"RUN"}` (STOP/RUN/PAUSE/ESTOP) |
| conveyor | cv, state | `{"type":"conveyor","cv":2,"state":"HOLD"}` (EMPTY/ARRIVING/HOLD/DEPARTING) |
| robot | robot, state, job | `{"type":"robot","robot":1,"state":"BUSY","job":"ROBOT1_POWERPACK_MOUNT"}` |
| result | run_no, ng, reason | `{"type":"result","run_no":12,"ng":true,"reason":"TURRET_MISSING"}` |
| alarm | source, code, msg, cleared | `{"type":"alarm","source":"robot2","code":"ERR","cleared":false}` |
| link | gateway, plc, robots | `{"type":"link","plc":true,"robots":[true,true,false]}` |

- 하트비트 (가정): 게이트웨이는 1초마다 필드 없는 `{"type":"link","ts":...}`를 보낸다. 웹은 어떤 이벤트든 2초 동안 오지 않으면 게이트웨이 끊김으로 표시한다 (W0-4의 3초 목표)
- `link`의 빠진 필드는 "바뀌지 않음"으로 본다 (부분 갱신)
- 작업 코드(`job`): `ROBOT1_HULL_PLACE`, `ROBOT1_POWERPACK_MOUNT`, `ROBOT2_TURRET_MATE`, `ROBOT2_WELD_MOTION`, `ROBOT3_SORT` (라인 PRD P0-3)
- 변수 규칙은 PC팀 1주차 결정을 따름 (가정: JSON 키는 snake_case, 상태 값은 대문자)
- 아직 정하지 않은 것
    - 게이트웨이와 웹 서버를 한 프로세스로 둘지
    - 비전 판정이 게이트웨이로 오는 경로 (PLC 경유 또는 직접)
    - NG 사유 코드 목록 (비전·PLC팀과 합의)
    - 로봇 제어 방식: PLC REQ → 게이트웨이가 Python IndyDCP3로 지시로 결정 (2026-09-30, Conty 앱 사용 안 함). 로봇 상태는 게이트웨이가 직접 알므로 `robot` 이벤트는 게이트웨이가 만든다
    - 작업 코드의 부가 정보: 라인 PRD P0-3은 `ROBOT1_POWERPACK_MOUNT`+슬롯, `ROBOT2_TURRET_MATE`+슬롯, `ROBOT3_SORT`+PASS/FAIL. `robot` 이벤트에 선택 필드(`slot` 등)를 둘지 게이트웨이 담당과 합의
    - 팔레트 위치 레코드: 라인 PRD P0-1에서 PLC가 위치별 레코드 `{module_id, turret_id, step, ng}`를 이월함. 이것을 이벤트로 받으면 웹의 순서 기반 팔레트 추정(현재 가정)을 없앨 수 있음. I/O 할당표 확정 시(M4) 제안
    - 3D 모델: 컨베이어 GLB는 있음. 트레이·보관창고·전차는 트윈 작업에서 만듦 (계획 B1·B2). 보관창고는 CV5 끝의 서보 승강기로 3칸 (2026-09-30 확정). 트레이 위치·구획은 라인 PRD에서도 미정
    - 보관창고 선반 신호: 벨트에 맞춘 칸, 이동 중 여부, 칸별 적재 여부를 PLC에서 받을지. 받는다면 `storage` 이벤트 추가를 제안
      (예: `{"type":"storage","level":2,"moving":false,"slots":[true,false,false]}`, `level` = 지금 벨트 높이에 맞춘 칸). 합의 전까지 웹은 CV5 EMPTY 횟수로 적재 수를 추정하고, 아래 칸부터 채우며, 선반은 다음 빈 칸을 벨트에 맞춰 둔다고 가정
    - 보관창고에서 팔레트를 꺼내는 방법과 신호 (작업자 수동 가정)
    - GLB 치수가 라인 PRD 가정보다 약 2배 큼 (벨트 폭 240 vs 100 mm, 팔레트 280 vs 약 120 mm). 디자인팀 확인 필요
